# Keybinding rendering into `views-shell.d` slots

A plugin declares keybindings compositor-neutrally in `contributes.keybindings`
(a command and a key). views-shell renders them per compositor into **slot files**. The
user's dotfiles include each slot once. views-shell writes only the slot files, never the
user's config.

## Principles

1. **Slots, not ownership.** The real config stays in the dotfiles. They declare
   the include lines and the default `$views_shell_*` variables. views-shell writes only the files
   those lines include. Home Manager declares the include lines and never owns the
   generated files.
2. **One file per plugin per slot.** Enable writes it. Disable or remove deletes
   it. A plugin with no keybindings has no file.
3. **Write first, then apply.** views-shell writes the file, then applies: a live binding
   where the compositor allows one, otherwise a reload. A reload discards runtime
   bindings and scroll's Lua state, which is why the file is always written first.
4. **The user wins.** The slot include sits **before** the user's own bind block, so
   a hand-written binding overrides a slot binding. The shortcuts page shows those
   as locked, with their file and line.
5. **Conflicts block enable.** `views-shell plugin check` compares every slot fragment and
   the compositor's live bindings. A conflict blocks `views-shell plugin enable`.
6. **One writer.** The views-shell process is the only writer of slot files
   (rule R8). `views-shell plugin render --out <dir>` produces the same files at Nix build
   time from a declared enabled set, for read-only configs.

## Paths (PROPOSED, see P8)

| Compositor | Include line in the user's config | Slot file per plugin |
|---|---|---|
| scroll | `include ~/.config/scroll/views-shell.d/*.conf` | `~/.config/scroll/views-shell.d/<plugin-id>.conf` |
| sway | `include ~/.config/sway/views-shell.d/*.conf` | `~/.config/sway/views-shell.d/<plugin-id>.conf` |
| niri | `include "views-shell.kdl"` (niri versions with config includes) | `~/.config/niri/views-shell.kdl`, one generated file holding every enabled plugin's stanza, each fenced by a comment naming the plugin |
| Hyprland | `source = ~/.config/hypr/views-shell.conf` | `~/.config/hypr/views-shell.d/<plugin-id>.conf`, sourced from a generated `views-shell.conf` |
| menus | (none: views-shell reads them) | `$XDG_STATE_HOME/views-shell/slots/menu/<plugin-id>.json` |
| launcher | (none) | `$XDG_DATA_HOME/applications/views-shell-<plugin-id>-<command>.desktop`, marked `X-views-shell-Managed=true` |

The default variables the dotfiles set on scroll and sway:

```
set $mod Mod4
set $views_shell_rail_width 56
```

## Key translation

| Neutral | scroll and sway | niri | Hyprland |
|---|---|---|---|
| `Mod` | `$mod` | `Mod` | `$mainMod` |
| `Super` | `Mod4` | `Super` | `SUPER` |
| `Ctrl` | `Ctrl` | `Ctrl` | `CTRL` |
| `Alt` | `Mod1` | `Alt` | `ALT` |
| `Shift` | `Shift` | `Shift` | `SHIFT` |
| `Return` | `Return` | `Return` | `Return` |
| `Comma` | `comma` | `Comma` | `comma` |
| letters | lower case | upper case | upper case |

## Dispatch per compositor

On scroll and sway, a binding uses `nop`. The `nop` command does nothing in the
compositor but emits a `binding` event over IPC, which views-shell reads. Nothing forks
per keypress, the keys stay the compositor's (so locked, release and mode
bindings work), and the binding is harmless when views-shell is not running. On niri and
Hyprland there is no binding event, so the binding runs `views-shell call`.

Every `nop` payload starts with `views-shell`, then the plugin id, the command and
optional JSON arguments: `nop views-shell <plugin-id> <command> [<json>]`.

## Worked example

`example.power-menu` declares:

```json
"keybindings": [
  { "command": "toggle", "key": "Mod+Shift+Escape" },
  { "command": "lock", "key": "Mod+Ctrl+L", "locked": false }
]
```

**scroll** (`~/.config/scroll/views-shell.d/example.power-menu.conf`):

```
# Generated by views-shell for example.power-menu 0.1.0. Do not edit: changes are
# overwritten. Disable the plugin or override the key in your own config.
bindsym $mod+Shift+Escape nop views-shell example.power-menu toggle
bindsym $mod+Ctrl+l nop views-shell example.power-menu lock
```

**niri** (inside `~/.config/niri/views-shell.kdl`):

```kdl
// begin example.power-menu (generated by views-shell)
binds {
    Mod+Shift+Escape { spawn "views-shell" "call" "example.power-menu" "toggle"; }
    Mod+Ctrl+L { spawn "views-shell" "call" "example.power-menu" "lock"; }
}
// end example.power-menu
```

**Hyprland** (`~/.config/hypr/views-shell.d/example.power-menu.conf`):

```
bind = $mainMod SHIFT, Escape, exec, views-shell call example.power-menu toggle
bind = $mainMod CTRL, L, exec, views-shell call example.power-menu lock
```

## Flags

| Field | scroll and sway | niri | Hyprland |
|---|---|---|---|
| `release: true` | `bindsym --release` | not supported: the entry is not registered | `bindr` |
| `locked: true` | `bindsym --locked` | `allow-when-locked=true` | `bindl` |
| `mode: "<name>"` | inside `mode "<name>" { … }` | not supported | inside a submap |
| `when` | evaluated by views-shell at dispatch; the binding is always present | same | same |

## Lua slot (scroll only)

A plugin that ships scroll Lua (capability and permission `scroll.lua`) gets a
`lua` line in the same slot file, so the script re-runs after every reload:

```
lua ~/.local/share/views-shell/plugins/example.power-menu/scroll/on_idle.lua
```

Runtime `LUA_EVAL` is reserved for plugins that declare `scroll.lua.eval`. It is
never reachable from Chrome or the native messaging host.

## Gestures

Gestures emit no binding event, so they render to `exec views-shell call …` on every
compositor:

```
bindgesture swipe:3:up exec views-shell call views-shell.launcher toggle
```
