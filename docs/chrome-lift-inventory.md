# Chrome lift inventory

Survey tag: Chromium **154.0.8037.92** (Linux Stable, commit `334b65d254ccc35df4fca82706d1753227b01039`), read on the bench host at `~/chromium/src`. Every path below is cited as the sweeps read it; every line count is a `wc -l` of the files named, excluding tests unless stated.

## The additive rule

views-shell is a Views C++ program, not a browser (R24): one content-free process, no `//content`, no Blink, no V8, and it never links `//chrome` or `//ash`. It is **additive**: Chrome's and Ash's Views files may be *copied* into the tree, each keeping its "Copyright … The Chromium Authors" BSD-3 header (R7) plus a provenance line, and decoupled from `Browser`, `Profile`, `TabStripModel`, `WebContents`, feature flags and metrics. Tom's words: "we are additive. it's a views c++ material!" and "i want the entire views shell exemplars, broken down into components, that become the whole shell!"

Three verdicts are used throughout:

- **lift as is** — copied unchanged apart from namespace, export macro and BUILD target (0 cuts), or already linked because it lives in a Linux-buildable `//ui` or `//components` directory.
- **lift and decouple** — copied, then cut. A *cut* is one dependency removed or replaced; the count is the size measure, together with lines. No time or effort figures appear in this document (R21).
- **stock twin instead** / **skip** — not copied; the stock control or a re-authored view covers it, or nothing in the shell needs it.

## Link versus copy

| Source | Linkable? | What to do |
|---|---|---|
| `//ui/views`, `//ui/color`, `//ui/base`, `//ui/message_center`, `//ui/message_center/vector_icons`, `//components/vector_icons` | yes | link as is; not ledgered |
| `//components/global_media_controls`, `//components/media_message_center`, `//services/media_session`, `//components/infobars/core`, `//components/tab_groups` | yes (content-free targets) | link as is; not ledgered |
| `//chrome/browser/ui/views/**`, `//chrome/browser/ui/**`, `//chrome/app/vector_icons`, `//chrome/common/themes` | never (R24) | copy single files; every copied file gets a ledger row |
| `//ash/**`, `//ui/chromeos/styles` | never (`assert(is_chromeos)`) | copy single files; ledger row |
| `//ui/views/controls/webview`, `//components/constrained_window`, every `webui_*` and `*WebUI*` file | pulls `//content` | out |

Chrome's BUILD.gn targets cannot be reused: `chrome/browser/ui/views/tabs/*/BUILD.gn` `:impl` sets, `toolbar:impl`, `side_panel:side_panel`, `download`, `global_media_controls`, `media_router`, `bookmarks` and `location_bar` all `public_deps` on `//content/public/browser`. Copied files get fresh views-shell targets; the only Chrome `.gn` worth reusing is the `aggregate_vector_icons` template in `//components/vector_icons/vector_icons.gni`.

## Findings

Verbatim from the sweeps, the vertical tab strip first.

### Tabs (`chrome/browser/ui/views/tabs/**` plus `frame/vertical_tab_strip_*`, `ui/tabs/vertical_tab_strip_*`, `ui/tabs/tab_style*`, `views/animations/tab_strip_animations*`)

- Vertical tabs at 154.0.8037.92 have no base::Feature of their own. They are gated by the user pref prefs::kVerticalTabsEnabled ('vertical_tabs.enabled', chrome/common/pref_names.h:1248). VerticalTabStripStateController::ShouldDisplayVerticalTabs() just returns that pref (vertical_tab_strip_state_controller.cc:180-182), so the earlier flag has been launched and removed. The remaining flags are kVerticalTabsNewBadge (ENABLED_BY_DEFAULT) and kVerticalTabsExpandOnHover (DISABLED_BY_DEFAULT), whose params are a 350 ms delay, a velocity heuristic (on by default, threshold 0.25 dp/ms, minimum 3 samples, 10 ms sampling, 12 px edge distance, 200 ms edge delay) and a click delay of 0 (chrome/browser/ui/tabs/features.cc:33-87). This code does not confirm the 'since 151' date.
- The vertical strip is built from three layers. (1) A frame-level VerticalTabStripRegionView (chrome/browser/ui/views/frame/, 1440 lines) owns resize, collapse animation and expand-on-hover, and implements VerticalTabStripStateController::Delegate. (2) A rail header and footer in chrome/browser/ui/views/tabs/vertical/ (top container, bottom container, scroll bar, focus swipe, hover lock; 1259 lines without tests). (3) The orientation-agnostic tab tree in chrome/browser/ui/views/tabs/common/ (TabCollectionNode, TabStripView, the pinned and unpinned containers, TabView, TabGroupView, SplitTabView, the animating layout manager and drag), which takes TabStripOrientation::kVertical. The vertical row shape is VerticalTabStyleViews: a plain RRect fill (247 lines), compared with HorizontalTabStyleViews' 966-line curved-tab path.
- Geometry to copy into style tokens. The rail is 56 px collapsed, 126 px minimum and 400 px maximum uncollapsed, 240 px by default, and snaps within 15 px of the default. The resize handle is 5 px (2 px collapsed) and the keyboard resize step is 50 px. Rows are 30 px tall (32 px pinned) with an 8 dp corner radius and 32 px minimum width. Rail horizontal padding is 12; vertical padding is 12 uncollapsed and 8 collapsed. Button icons are 20 dp (18 dp for the combo button). New-tab and collapse buttons are 32 px; top-container buttons are 28 px; flat-edge padding is 2. Sources: vertical_tab_strip_region_view.h:64-72, .cc:80-83 and layout_constants.cc:148-179.
- Animation timings for the rail, from TabStripAnimations::kVerticalTabStrip (chrome/browser/ui/views/animations/tab_strip_animations.cc:58-135). kExpand runs 400 ms and kCollapse 350 ms with EASE_IN_OUT_EMPHASIZED (300 and 250 ms with ACCEL_80_DECEL_20 under the side-panel flyover flag). kExpandOnHover runs 250 ms and kCollapseOnHover 200 ms. Corner and top keyframes sit at 25% and 75%, and opacity fades over 100 ms. These run on chrome/browser/ui/animation's BrowserAnimationController, a chrome-only keyframe framework that the shell does not have: either port it or replace it with gfx::SlideAnimation (one decoupling cut).
- TabCollectionAnimatingLayoutManager (common/, 1074 lines) depends on nothing in chrome: its .cc includes only its own header. It interpolates child layouts for add, remove and reparent and is the best drop-in for every animated list in the shell. RoundedScrollBar (242 lines), TabStripLayout and TabWidthConstraints, GlowHoverController, FadeLabelView and FilenameElider are also nearly free of coupling.
- The unified tab tree is keyed on components/tabs TabCollection (tabs::ConstChildPtr). tab_collection.h includes tab_interface.h, and tab_interface.h:17 includes content/public/browser/web_contents_user_data.h, so components/tabs cannot be linked in a content-free process. The node tree has to be retyped onto a shell model (a variant of workspace, group, split and window). This is the main cut, and the rest of common/ follows from it.
- tabs::kTabStripUnification (DISABLED_BY_DEFAULT, features.cc:89) is what makes Chrome build only the active region view, and it moves the horizontal strip onto the same common/ components (BrowserView::ShouldDrawTabStrip, browser_view.cc:1419-1432). The legacy horizontal stack (TabStrip, Tab, TabContainerImpl, BrowserTabStripController and the legacy group views; about 15.5k lines, heavily tied to Browser and TabStripModel) is therefore not worth lifting. A horizontal workspace strip should be built from common/ in kHorizontal orientation.
- Tab search in this tree is only an entry point. TabStripComboButton hosts TabSearchBubbleHost, which is a WebUI bubble (chrome/browser/ui/webui/tab_search), so there is no Views tab-search UI to lift. The combo button's two-segment flat-edge geometry is liftable; its content is not.
- Build structure: chrome/browser/ui/views/tabs/{common,vertical,tab,shared,hovercard,groups,horizontal,dragging,organizer,glic} each have their own BUILD.gn, split into a header-only source_set and an ':impl' source_set. The ':impl' deps pull //content/public/browser, //chrome/browser/glic, //chrome/browser/ui/tabs/organizer:impl and //components/performance_manager (vertical/BUILD.gn and common/BUILD.gn). Copied files need a fresh BUILD.gn in views-shell. Nothing here is generated, apart from grit string and resource ids (IDS_*, IDR_THEME_TOOLBAR, actor_browser_resources), which need replacing.
- The rail's hit testing understands the caption area. VerticalTabStripRegionView::IsPositionInWindowCaption and the top container's caption_button_width x toolbar_height exclusion rectangle let empty rail space drag the window and keep buttons clear of the leading caption buttons. This is useful if the shell's rail shares a surface with a client-side caption, and harmless otherwise.
- Expand-on-hover uses a lock system: ExpandOnHoverLockType has kForceCollapse, kKeepCurrentState and kKeepExpanded (tab_strip_region_view.h:27-42). Bubbles, context menus, drags and the omnibox popup take locks so the overlay does not collapse under the user. The rail needs this, for example while a launcher or menu is open.
- The focus swipe (VerticalTabStripFocusSwipeController, 219 lines) is a two-finger horizontal swipe on the rail that rotates the 'focused tab group'. It is gated on features::kTabGroupsFocusing and uses mouse wheel events on Win, Linux and ChromeOS and scroll events on Mac, with a 15 px axis lock, a 75 px trigger and a 300 ms reset. It is a cheap pattern for swiping between workspaces on the rail, once the TabStripModel call is replaced.
