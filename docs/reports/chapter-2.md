## What the tiny library costs now

The browser-free build is checked, twice over. `views_shell` links no `//content`, no Blink renderer, no V8, no `//chrome` and no `//ash`: `assert_no_deps` holds at `gn gen`, and `gn path` prints `No non-data paths` for all five trees in both build directories. It is a production program now. The test context factory is gone (debt D1 paid): `shell/app/views_shell_context_factory.cc` is an in-process viz host after `components/viz/demo`, `testonly = false`, and `gn desc deps --all` names no `test_support`. It acks its Wayland configures without the test workaround, so finding F2 is closed the faithful way. Software compositing is the default and needs no GL at all; GPU compositing is a flag and also draws.

Sizes. The release build (`out/release`, non-component) is 88.7 MB as linked and 63.3 MB stripped, beside 66.0 MB for stock `views_examples`: the shell costs what Google's own examples program costs, because both carry the same viz, GPU and service closure. A package for a seat is about 84 MB on disk (the binary, ICU, ANGLE, SwiftShader, the Vulkan loader, the pak). The dependency graph is 6,417 targets, 3,532 of them under `//third_party`; `//ui/views` itself is ten. The heavy trees that a shell does not want enter through `//components/viz/service`: WebRTC (755 targets, through media capture) and XNNPACK, TFLite, ruy and LiteRT (about 680, through the WebNN service). Those edges stay until they are cut the way F3 cut the Blink edges; that cut is the first candidate for shrinking the library further.

Footprint, the same `--bar` program across the four measurements, idle, one sample each: chapter 1's test-factory build was 141 MB PSS, 30 threads, 344 FDs. The production host in software compositing is 107 MB, 15 threads, 352 FDs (component build). The GPU-fair run, with the render node bound and a gles2 compositor, is 128 MB for the same frame: on this build the GPU path costs memory rather than saving it. The release build of the whole assembled program (adapter, model, notification daemon, bar) is 59.7 MB PSS, 0 % CPU, 0 context switches a second, 17 threads and 69 FDs. The 344-FD question is answered: `base::debug::EnableInProcessStackDumping()` pre-opens one read-only descriptor per mapped module, 321 of them in a component build and 39 in release; it is a steady allocation, not a leak, and it is kept so a crash in the shell's own unit symbolizes.

Unit tests: 139 ran green on the bench in one `views_shell_unittests` binary, against fake sockets, a 97-frame transcript recorded from stock scroll, a private session bus and a private headless scroll.

## What draws on stock scroll, and what was typed into it

Stock scroll 1.13-dev, no patch, headless under `runtime-test`. `views_shell --bar --theme <omarchy theme dir>` draws a 32 px top layer surface with an exclusive zone, in the theme's colours: the ground is the theme's `background` to 99.8 % of its rows (`#1a1a1a` for claude-dark, `#000000` for all-black and noir, `#f9f9f7` for claude-light), the clock in the theme's foreground, with no colour literal in the code. The bar's left section is a workspace strip fed by the scroll adapter over i3-ipc; the program asked for workspace 3, the compositor echoed it (`ECHO workspace 3`), the strip followed the snapshot, and the compositor's window list held no views-shell window. A `notify-send` from the bench became its own overlay layer surface at the top right (`views-shell-notification`, 360x82) and was destroyed on expiry. `--demo-popup` opened a stock menu that became an `xdg_popup` parented to the bar, wearing the theme. `--demo-keyboard` opened an exclusive-keyboard overlay surface with a `views::Textfield`, and `wtype` typed `hello` into it: `wl_keyboard.enter` arrived, the widget activated through the layer-shell patch's `OnKeyboardFocusChanged`, and the log read `TYPED h` through `TYPED hello`. That is the credential modal's one risk, and it is retired. A run with no surface flag exits 2 with the rule-R1 message. With `--run-for-seconds=12` the program exited 0 on its own, so the reverse teardown is clean.

Beside the pixels: the plugin protocol is settled by a conformance runner that plays views-shell over stdio against the three T2 example plugins inside `tools/validate.sh`; the C++ plugin host spawns the echo plugin, routes a command, refuses an undeclared `exec` with -32001 and shuts it down; the ui-tree renderer draws every example tree onto stock Views and its trace equals the Python reference's goldens byte for byte, with every node stock Views cannot draw reported as a render error with a reason; the registry view of every manifest is reproduced byte for byte too; `shell/` holds only what is built or applied (47 lifted files deleted, recoverable by commit); and `PROVE.md` is 141 rows that `tools/prove.sh` can re-run.

## What was refuted

The expectation that the production context factory would cut the FD count: it did not (352 and 364 against 344), and the census says why. The idea that a GPU path saves memory on this build: it costs 20 to 33 MB more. Chapter 1's window mode (C3.4): superseded, the program draws only on layer surfaces and exits otherwise. Three claims as the briefs wrote them could not pass: the notifications test command (`dbus-run-session` inside the FHS environment fails, and Views tests need a Wayland display on this Wayland-only Ozone build), the examples README check (`examples/themes` is not a plugin), and the community-theme light-mode check (no Omarchy theme ships a `light.mode` file; the light ones set `mode = "light"` in `colors.toml`). The first two were re-proven in scoped form; the third item never merged. Two warnings about the tree: `tools/validate.py` accepts only lowercase hex and rejects gradients that Omarchy accepts, so seven of Omarchy's 22 themes fail the repository gate as they are; and the examples name eight icons that only Ash ships, so the power menu and the music button draw without their icons until that subset is ported.
